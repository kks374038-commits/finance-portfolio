# Контракты данных и границы прототипа

## 1. Единицы и значения

Суммы передаются десятичными строками: `"1234.56"`, а не JSON float. Актив указывается явно. Все даты-время содержат часовой пояс. Ноль отличается от `null`: последний означает отсутствие значения.

Для промышленной системы отдельно хранятся `occurred_at` (факт), `booked_at` (отражение), `received_at` (получение) и `as_of` (момент остатка). Для блокчейна нужны сеть, статус подтверждения и правило финальности провайдера.

## 2. Вход расчётного ядра

Файл `examples/demo_input.json` содержит `cutoff_at`, `currency_rules`, `accounts`, `routes`, `internal_transfers`.

| Поле кассы | Тип / смысл |
|---|---|
| account_id | Уникальный стабильный ID логического субсчёта |
| entity_id | Владелец/юридическое лицо; не имя держателя в публичных примерах |
| kind, currency, network | Банк/кошелёк, актив и сеть |
| source_mode | В демо только API_FIXTURE или MANUAL_FIXTURE |
| source_status | received либо missing |
| snapshot_at | Момент внешнего остатка, сопоставимый с cutoff_at |
| opening, credits, debits | Начальный остаток и подтверждённые движения периода |
| book_closing | Независимый конечный остаток учётной системы |
| external_balance | Внешний общий остаток либо null |
| available | Доступный остаток по семантике источника |
| internally_reserved | Внутренний резерв, ещё не исключённый провайдером |
| operating_buffer | Защищённый операционный минимум |
| target_balance | Цель по полезному остатку после внутренних резервов |
| movement_complete | Подтверждение полноты движений; false блокирует планирование |
| account_status | active либо restricted |
| oldest_available_lot_at | Дата старейшего доступного лота либо null |
| aging_method | fifo_lots для тестового подтверждённого признака |
| source_batch_id | Ссылка на пакет происхождения |

`currency_rules`: quantum — минимальная единица, tolerance — допуск, idle_days — порог сигнала, min_transfer — минимум заявки. Они задаются по активу, не являются универсальными нормативами.

Дата лота в демо поставляется фикстурой. Ядро не восстанавливает её из банковской выписки и не рассчитывает сумму каждой возрастной корзины. Дата последней активности не используется как замена возрасту остатка.

## 3. Ручной файл

`examples/manual_upload_example.csv`: UTF-8 с BOM, одна строка на кассу, заголовки `account_id,currency,snapshot_at,external_balance,available,source_batch_id`.

Это пример структурированного входа адаптера. Импорт произвольных файлов в текущем ядре не реализован. Перед промышленным применением нужны профили форматов, сопоставление полей, проверка периода и актива, хеш пакета, журнал ошибок и подтверждение применения.

## 4. API-фикстура

`examples/api_response_fixture.json` содержит `simulation: true` и 80 строк тестовых данных. Это не ответ конкретного банка и не обращение к рабочему API.

Реальный адаптер должен возвращать нормализованные строки вместе с метаданными всех страниц: диапазон, финальность статуса, as_of, число строк, checksum/raw_reference, успех/ошибку и подтверждение полноты. Неполная пагинация не может иметь статус успешной загрузки.

## 5. Связанные переводы

`transfer_id`, `source`, `destination`, `source_asset`, `destination_asset`, `link_method`, `book_credit`, `debit_event`, `credit_event`, `return_event`.

Событие: `external_id`, `amount`, `status`. В учебном проверяющем модуле суммы ног — основной перевод без комиссии, комиссия сверяется отдельно. `posted` считается подтверждённым в пределах демонстрации; адаптер промышленного источника обязан объяснить соответствие реальной финальности.

Ядро не ищет пары по приблизительным суммам: оно проверяет уже предложенную связь. Допустимы `external_reference` и `confirmed_manual_link`. Связь только по сумме и дате остаётся `AMBIGUOUS_LINK`.

## 6. Маршрут заявки

`route_id`, `source`, `destination`, `asset`, `fee`, `limit`, `enabled`, `priority`.

В демо комиссия списывается с донора в том же активе. `net_amount` — чистое зачисление, `source_debit = net_amount + fee`. Другой актив комиссии, банковский календарь, сроки перевода, минимумы провайдера, сетевой gas и конвертации требуют расширенного адаптера/политики и в демо не исполняются.

## 7. Выход

`reports/demo_result.json`: 100 проверенных позиций со статусами, исходными значениями и кодами ошибок; раздельные полученные суммы по активам; проверки переводов; проекты заявок; ограничения прототипа.

Полученные внешние итоги могут содержать строки с выявленными ошибками. Они подписаны `external_received`, а не «подтверждённая свободная ликвидность». Платёжные действия отсутствуют.

## 8. Проект внутренних интерфейсов целевой системы

Это предлагаемые интерфейсы создаваемого сервиса, не существующие банковские endpoints:

- `POST /imports/manual` — зарегистрировать файл и предпросмотр;
- `POST /imports/{batch_id}/confirm` — применить проверенный пакет;
- `POST /reconciliation-runs` — запустить версионируемый расчёт;
- `GET /reconciliation-runs/{run_id}` — результат и исключения;
- `POST /transfer-proposals` — создать черновик с идемпотентным ключом;
- `POST /transfer-proposals/{id}/approve` — согласовать с повторной проверкой полномочий и резервов.

Публичный прототип этих HTTP-интерфейсов не содержит. Реальные API банков определяются только по их документации и выданным правам.
